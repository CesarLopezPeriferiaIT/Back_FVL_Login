Microservicio de login

Fundación Valle del Lili · Guía técnica de consumo · API v1

Ambientes: desarrollo (dev), calidad (qas) y producción (prd). El prefijo es /backend/{ambiente}/v{version}/, por ejemplo /backend/dev/v1; depende de APP_ENV y API_VERSION. Las rutas públicas de diagnóstico / y /health no llevan prefijo.

Formato de respuesta

message es el texto legible; error es null en éxito o un objeto con codigo estable y detalles, arreglo de cadenas; code es 0 en éxito o el estado HTTP en error; data contiene el resultado o null. 

{"message":"Servicio disponible.","error":null,"code":0,"data":{"servicio":"login","version":1,"ambiente":"dev"}}
{"message":"Correo o contrasena incorrectos.","error":{"codigo":"CREDENCIALES_INVALIDAS","detalles":[]},"code":401,"data":null}

Autenticación y convenciones

API Key del cliente

Registre una instalación y envíe su clave en X-API-Key en cada ruta protegida. La clave en texto plano se entrega una sola vez; almacénela de forma segura. La base de datos conserva únicamente su hash SHA-256 y los registros identifican la clave por sus primeros ocho caracteres.

Alcances por cliente
Alcance Clientes
auth:register, auth:login, auth:confirm-email, auth:refresh, auth:logout, auth:password-reset mobile, web-bff
auth:me mobile, web-bff, web

Token de acceso del usuario

Envíe Authorization: Bearer <token> cuando se indique. La vigencia predeterminada del acceso es 15 minutos y la del refresh token es 30 días, ambas configurables. El refresh se almacena hasheado y rota al renovarse: el anterior queda invalidado y se extiende la vigencia. Proteja ambos tokens.

Las peticiones con cuerpo y las respuestas usan JSON. Las rutas están en inglés y emplean guiones medios; las fechas son UTC en ISO 8601 y los identificadores son UUID. Los ejemplos usan el prefijo de desarrollo. Use HTTPS en los ambientes desplegados.

Las rutas protegidas pueden responder con API_KEY_REQUERIDA, API_KEY_INVALIDA, API_KEY_REVOCADA o API_KEY_SIN_PERMISO; las que exigen Bearer también con TOKEN_REQUERIDO o TOKEN_INVALIDO. Cualquier ruta puede responder ERROR_INTERNO. Estos errores comunes se aplican además de los indicados por operación.

Catálogo de endpoints

GET /

Pública; sin cabeceras ni cuerpo. Devuelve 200 con datos del servicio.

GET / HTTP/1.1

HTTP/1.1 200 OK
{"message":"Servicio disponible.","error":null,"code":0,"data":{"servicio":"login","version":1,"ambiente":"dev"}}

Errores: error interno imprevisto.

GET /health

Pública; sin cabeceras ni cuerpo. Se usa en el healthcheck de Docker.

GET /health HTTP/1.1

HTTP/1.1 200 OK
{"message":"Servicio saludable.","error":null,"code":0,"data":{"estado":"ok","ambiente":"dev","version":1}}

Errores: error interno imprevisto.

POST /backend/dev/v1/installations/register

Pública. Cabecera Content-Type: application/json. Cuerpo obligatorio: nombre, cadena de 1 a 128 caracteres; tipo_cliente, cadena mobile, web-bff o web. 

POST /backend/dev/v1/installations/register HTTP/1.1
Content-Type: application/json

{"nombre":"Aplicación móvil","tipo_cliente":"mobile"}

HTTP/1.1 201 Created
{"message":"Instalacion registrada.","error":null,"code":0,"data":{"api_key":"CLAVE_EJEMPLO","tipo_cliente":"mobile","permisos":["auth:register","auth:login","auth:confirm-email","auth:refresh","auth:logout","auth:password-reset","auth:me"],"fecha_creacion":"2026-11-11T12:00:00.000Z"}}

Errores: VALIDACION_FALLIDA, ERROR_INTERNO.

POST /backend/dev/v1/auth/register

Alcance auth:register; cabeceras X-API-Key y Content-Type: application/json. Cuerpo obligatorio: email cadena de correo válida, password cadena conforme a la política, tyc booleano. Si es false se crea la cuenta sin enviar confirmación; revise también el indicador de envío. 

POST /backend/dev/v1/auth/register HTTP/1.1
X-API-Key: CLAVE_EJEMPLO
Content-Type: application/json

{"email":"usuario@example.org","password":"Ejemplo123","tyc":true}

HTTP/1.1 201 Created
{"message":"Registro realizado.","error":null,"code":0,"data":{"usuario":{"uuid":"123e4567-e89b-12d3-a456-426614174000","email":"usuario@example.org","estado":"C","tyc":true,"fechaCreacion":"2026-11-11T12:00:00.000Z","fechaModificacion":"2026-11-11T12:00:00.000Z"},"correo_confirmacion_enviado":true}}

Errores adicionales: VALIDACION_FALLIDA, USUARIO_YA_EXISTE, RATE_LIMIT_EXCEDIDO.

POST /backend/dev/v1/auth/logout

Alcance auth:logout; cabeceras X-API-Key y Authorization: Bearer TOKEN_ACCESO; sin cuerpo. Es la única respuesta que incluye Clear-Site-Data. Se revoca la sesión para renovaciones; el JWT de acceso se verifica por firma y vigencia, por lo que debe descartarse en el cliente. 

POST /backend/dev/v1/auth/logout HTTP/1.1
X-API-Key: CLAVE_EJEMPLO
Authorization: Bearer TOKEN_ACCESO

HTTP/1.1 200 OK
Clear-Site-Data: "cache","cookies","storage"
{"message":"Sesion cerrada.","error":null,"code":0,"data":{"mensaje":"Sesion cerrada"}}

Errores: los comunes de API Key y Bearer y ERROR_INTERNO.

POST /backend/dev/v1/auth/forgot-password

Alcance auth:password-reset; cabeceras X-API-Key y Content-Type: application/json. Cuerpo obligatorio: email, cadena de correo válida. Para una solicitud válida responde 200 con mensaje genérico, exista o no la cuenta.

X-API-Key: CLAVE_EJEMPLO
Content-Type: application/json

{"email":"usuario@example.org"}

HTTP/1.1 200 OK
{"message":"Si la cuenta existe, recibira instrucciones.","error":null,"code":0,"data":null}

Errores adicionales: VALIDACION_FALLIDA.

POST /backend/dev/v1/auth/reset-password

Alcance auth:password-reset; cabeceras X-API-Key y Content-Type: application/json. Cuerpo obligatorio: token y nueva_password, cadenas. Revoca las sesiones del usuario. También acepta GET /backend/dev/v1/auth/reset-password?token=... con X-API-Key y sin cuerpo: valida el enlace sin modificar la contraseña y responde {"email":"usuario@example.org"} en data. 

POST /backend/dev/v1/auth/reset-password HTTP/1.1
X-API-Key: CLAVE_EJEMPLO
Content-Type: application/json

{"token":"TOKEN_RESETEO","nueva_password":"NuevaClave123"}

HTTP/1.1 200 OK
{"message":"Contrasena actualizada.","error":null,"code":0,"data":null}

Errores adicionales: VALIDACION_FALLIDA, TOKEN_INVALIDO.

Contraseñas, estados y seguridad

La contraseña tiene entre 8 y 72 caracteres, al menos una letra ASCII y un dígito y no admite espacios en blanco. Se almacena como hash argon2id, nunca en texto plano.

Estados de cuenta
Estado Significado
A Activa.
I Inactiva.
C Por confirmar; predeterminado al registrarse.
D Desactivada por diez intentos fallidos consecutivos. Un operador autorizado debe desbloquearla manualmente en la base de datos mediante db/scripts/unlock-user.sql; el procedimiento también reinicia el contador de intentos fallidos.

El inicio de sesión limita solicitudes por correo e IP, con un umbral predeterminado mayor para IP; el registro también limita por IP. Al superarlo se responde 429 con RATE_LIMIT_EXCEDIDO. CORS utiliza una lista explícita de orígenes. La aplicación configura Helmet, CSP restrictiva, HSTS, protección contra marcos y MIME, políticas de referencia y recursos, y Cache-Control: no-store. Las duraciones predeterminadas son 15 minutos para acceso y 30 días para refresh.

Errores emitidos por el servicio

CUENTA_INACTIVA 403 Cuenta inactiva.
CUENTA_DESACTIVADA 403 Cuenta bloqueada por intentos.

Variables de entorno

Consulte .envexample para la plantilla completa. Configure secretos mediante un mecanismo seguro; no los incluya en clientes ni imágenes. Fuera de desarrollo se requiere SMTP.

Ciclo completo con curl

Sustituya los marcadores por valores reales obtenidos de las respuestas y del correo. No publique claves ni tokens. Use una URL HTTPS fuera de desarrollo. 

BASE=http://localhost:3000/backend/dev/v1
curl -X POST "$BASE/installations/register" -H 'Content-Type: application/json' -d '{"nombre":"Cliente móvil","tipo_cliente":"mobile"}'
# Copie data.api_key en API_KEY en un entorno seguro.
curl -X POST "$BASE/auth/register" -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' -d '{"email":"usuario@example.org","password":"Ejemplo123","tyc":true}'
# Obtenga el token del enlace recibido por correo.
curl -X POST "$BASE/auth/confirm-email" -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' -d "{\"token\":\"$TOKEN_CONFIRMACION\"}"
curl -X POST "$BASE/auth/login" -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' -d '{"email":"usuario@example.org","password":"Ejemplo123"}'
# Copie data.token_refresh en REFRESH; sustituya el anterior por el nuevo tras renovar.
curl -X POST "$BASE/auth/refresh" -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' -d "{\"refresh_token\":\"$REFRESH\"}"
